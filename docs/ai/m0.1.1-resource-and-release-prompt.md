## 2. T1 · 构建并发资源化

### 2.1 新增 `scripts/build/threads.sh`

只读脚本，输出可直接 `eval` 的 shell 赋值；必须优先读 **Docker daemon**，不能用宿主 shell 的 `nproc` / `/proc/meminfo` 代替（RV-019 已实测宿主 shell cgroup 4c/8G，但 daemon 32c/123GiB）。

要求：

- 查询 `docker info --format '{{.NCPU}}'` 与 `{{.MemTotal}}`；daemon 不可用时 exit 1，不静默回退。
- 计算 `mem_gb = MemTotal / 1024 / 1024 / 1024`（整数）。
- 分级表：

| 级别 | 条件 | `YP_BUILD_THREADS` | `YP_PARALLEL_MAKE` |
|---|---|---|---|
| standard | `cpus >= 32` 且 `mem_gb >= 120` | `32` | `-j 16` |
| mid | `cpus >= 16` 且 `mem_gb >= 32` | `16` | `-j 8` |
| small | `cpus >= 8` 且 `mem_gb >= 16` | `8` | `-j 4` |
| legacy | 其他 | `4` | `-j 2` |

- 允许显式环境覆盖 `YP_BUILD_THREADS` / `YP_PARALLEL_MAKE`；覆盖值必须为正整数 / `-j <正整数>`，否则 exit 1。
- 输出示例（顺序固定）：

```text
RESOURCE_TIER=standard
RESOURCE_CORES=32
RESOURCE_MEM_GB=123
export YP_BUILD_THREADS=32
export YP_PARALLEL_MAKE='-j 16'
```

- 脚本本身不启动容器、不写文件、不下载。

### 2.2 改 `kas/base.yml`

把固定值改成环境覆盖 + 安全默认，保留 8GB 历史回退：

```bitbake
# 默认 4/-j2 仅用于 8GB 历史配额；标准机由 scripts/build/threads.sh 导出
BB_NUMBER_THREADS = "${@os.environ.get('YP_BUILD_THREADS', '4')}"
PARALLEL_MAKE = "${@os.environ.get('YP_PARALLEL_MAKE', '-j 2')}"
```

要求：

- 不得把 32/-j16 写死成所有机器默认；默认仍是 4/-j2，避免无环境变量时在 8GB 机器 OOM。
- 用 `kas shell` / `bitbake-getvar` 在真实容器内确认最终值来自环境变量，且 `BB_NUMBER_THREADS=32`、`PARALLEL_MAKE="-j 16"`。
- 不改 `DL_DIR`、`SSTATE_DIR`、`BB_HASHSERVE` 等其他契约。

### 2.3 接线 runbook / test prompt / verify-env

- `docs/runbook-new-machine.md` 步骤 7 在 `docker run` 前：


并保留“容器不加 `--cpus`/`--memory`”与 `docker inspect` 三项为 0 的核验。
- `docs/ai/m0-new-machine-test-prompt.md` 同步同一组命令；记录 `RESOURCE_TIER`、`RESOURCE_CORES`、`RESOURCE_MEM_GB`。
- `scripts/verify-env.sh` 已有 `RESOURCE source=docker` 与 `RESOURCE_PARTIAL`；本轮补充 `SUGGEST_BUILD_THREADS` / `SUGGEST_PARALLEL_MAKE`（调用 `scripts/build/threads.sh` 或同样分级），不要重复实现两套阈值。
- `scripts/ai-entry.sh` 与 `README.md` 只需指向 `AGENTS.md` §2.1，不再重复长表。

### 2.4 变量契约同步

## 3. T2 · 真实构建复验（32c/128G）

复用已有真实卷 `/workspace/m01-e1/downloads`（1288 文件）与 `/workspace/m01-e1/sstate`（6945 文件）；不要重新下载 11 GiB。若卷不存在，按 runbook 取回并记录，不得用空缓存冒充。

步骤：

1. `bash scripts/build/threads.sh` → 期望 `standard`、`32`、`-j 16`。
2. `docker run -d` 启动构建容器，**不加任何 CPU/内存限制**；`docker inspect` 三项必须 `0/0/0`。
3. `docker exec ... bitbake-getvar BB_NUMBER_THREADS PARALLEL_MAKE` → 期望 `32` / `-j 16`。
4. 跑两次 prod `kas build kas/yp.yml:editions/prod.yml`，第二次前 `rm -rf build`；记录：
   - 墙钟、`Tasks Summary`、`Sstate` 命中、`ERROR` 命中；
   - 构建期间 CPU 利用率（`docker stats`、`/proc/stat` 或 `pidstat` 任选，记录采样命令）；
   - 内存峰值（`docker stats` / cgroup `memory.peak`）；
   - 产物 ext4 大小与 `file` 输出；产物导出仓库外，不入库。
5. 与 RV-019 的 291s / 236s 对比；**没有实测加速就说没有，不得声称“更快”**。核心验收是“32 线程确实生效 + 容器无限制 + 无 OOM”，不是一定比 236s 快。
6. 4c/8G 回退验证：用 `NEGATIVE_ONLY` 容器（`--cpus=4 --memory=8g`）只验证 `threads.sh` 在显式覆盖下输出 `4` / `-j 2`，并跑 `bitbake-getvar` 或短任务；若没有完整 4c/8G 冷构建，写 `UNVERIFIED`，不冒充通过。
7. 若 OOM、任务失败或 `32` 未生效：开 `ISS-037`，先记录再修；不得把 32 核结果写成 PASS。
