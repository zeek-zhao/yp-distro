## 2. T1 · 并发改为 CPU + 内存分级

### 2.1 改 `kas/base.yml`

把现有的纯 CPU 表达式替换为内存感知分级。要求：

- 读取 **容器内 cgroup 内存限制**，不能只读 `/proc/meminfo`；Docker `--memory` 不会改写 `/proc/meminfo`，只读 proc 会把 8 GB 容器误判成 123 GiB 宿主。
- 优先读 cgroup v2 `/sys/fs/cgroup/memory.max`，再读 cgroup v1 `/sys/fs/cgroup/memory/memory.limit_in_bytes`；值为 `max` 或超出合理范围时，回退 `/proc/meminfo` 的 `MemTotal`。
- CPU 用 `oe.utils.cpu_count()`（bitbake 原生、已由 ISS-037 验证可在容器内取到 32）；若不可用则回退 `os.cpu_count()`，并保证至少 1。
- 分级表必须与本提示词 §2.2 的 `threads.sh` 一致：

| 级别 | 条件 | `BB_NUMBER_THREADS` | `PARALLEL_MAKE` |
|---|---|---|---|
| standard | `cpus >= 32` 且 `mem_gb >= 120` | `32` | `-j 16` |
| mid | `cpus >= 16` 且 `mem_gb >= 32` | `min(16, cpus)` | `-j max(1, threads // 2)` |
| small | `cpus >= 8` 且 `mem_gb >= 16` | `min(8, cpus)` | `-j max(1, threads // 2)` |
| legacy | 其他 | `min(4, cpus)` | `-j max(1, threads // 2)` |

- `PARALLEL_MAKE` 必须至少 `-j 1`，不得出现 `-j 0`。
- 保留 `oe.utils.cpu_count()` 的既有修复，不得回到 `os.environ.get('YP_BUILD_THREADS', ...)`；`YP_BUILD_THREADS` / `YP_PARALLEL_MAKE` 不再作为 bitbake 控制变量。

参考实现（可调整写法，但语义必须一致）：

```bitbake
def yp_mem_bytes(d):
    import os

    def _read(path):
        try:
            with open(path, "r", encoding="utf-8") as f:
                return f.read().strip()
        except OSError:
            return ""

    for path in (
        "/sys/fs/cgroup/memory.max",                    # cgroup v2
        "/sys/fs/cgroup/memory/memory.limit_in_bytes",  # cgroup v1
    ):
        raw = _read(path)
        if not raw or raw == "max":
            continue
        try:
            n = int(raw)
        except ValueError:
            continue
        if 0 < n < (1 << 60):
            return n

    for line in open("/proc/meminfo", "r", encoding="utf-8"):
        if line.startswith("MemTotal:"):
            return int(line.split()[1]) * 1024

    return 0

def yp_build_threads(d):
    import os
    cpus = oe.utils.cpu_count() or os.cpu_count() or 1
    mem_gb = yp_mem_bytes(d) // (1024 ** 3)
    if cpus >= 32 and mem_gb >= 120:
        n = 32
    elif cpus >= 16 and mem_gb >= 32:
        n = min(16, cpus)
    elif cpus >= 8 and mem_gb >= 16:
        n = min(8, cpus)
    else:
        n = min(4, cpus)
    return max(1, n)

BB_NUMBER_THREADS = "${@yp_build_threads(d)}"
PARALLEL_MAKE = "-j ${@max(1, int(d.getVar('BB_NUMBER_THREADS')) // 2)}"
```

如果 `os` 在当前 bitbake 配置作用域不可用，显式 `import os`；不要为了绕开作用域再引入环境变量注入。

### 2.2 改 `scripts/build/threads.sh`

改为只读诊断，输出建议值，不输出可 `eval` 的 `export`：

```text
RESOURCE_TIER=standard
RESOURCE_CORES=32
RESOURCE_MEM_GB=123
SUGGEST_BUILD_THREADS=32
SUGGEST_PARALLEL_MAKE='-j 16'
```

要求：

- 仍读 Docker daemon 的 `NCPU` / `MemTotal`；daemon 不可用时 exit 1，不静默回退。
- 分级表与 §2.1 完全一致，legacy 用 `min(4, cpus)`，不要固定 4；`SUGGEST_PARALLEL_MAKE` 至少 `-j 1`。
- 删除 `YP_BUILD_THREADS` / `YP_PARALLEL_MAKE` 的显式覆盖逻辑，不再输出 `export`；不声称“容器继承后注入 bitbake”。
- 脚本注释写清楚：这是 **daemon 级诊断**；实际 bitbake 在容器内按 cgroup 内存 + 可见 CPU 计算，负向容器下诊断值与实际值可能不同，最终以 `bitbake-getvar` 为准。

- 继续调用 `threads.sh`，但解析 `SUGGEST_BUILD_THREADS=` / `SUGGEST_PARALLEL_MAKE='`，不再解析 `export YP_...`。

- 如果无法保证诊断值与容器内实际值一致，宁可删除 `SUGGEST_*` 段，也不要给错值。

### 2.4 同步变量契约与门禁

- `scripts/check-vars.sh`：断言 `kas/base.yml` 含 `yp_build_threads(d)`、`BB_NUMBER_THREADS = "${@yp_build_threads(d)}"`、`PARALLEL_MAKE = "-j ${@max(1, int(d.getVar('BB_NUMBER_THREADS')) // 2)}"`，且含 cgroup 内存路径；断言不再含 `os.environ.get` / `YP_BUILD_THREADS`。

- 不要为了让门禁通过而放宽为永远通过。
