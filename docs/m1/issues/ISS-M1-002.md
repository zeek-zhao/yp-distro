## 1. 现象

首次 `kas build kas/yp.yml:kas/editions/dev.yml`（后台日志 `/work/build-dev.log`）在任务约 2071/4775 处失败：

```
ERROR: llvm-project-source-22.1.8-r0 do_unpack: Bitbake Fetcher Error: UnpackError(
  'xz -dc /work/downloads/llvm-project-22.1.8.src.tar.xz | tar --extract --no-same-owner -f - failed with return value 2', ...)
log.do_unpack: Killed / tar: Unexpected EOF in archive / tar: Error is not recoverable
BUILD_RC=2
Tasks Summary: Attempted 2071 tasks of which 0 didn't need to be rerun and 1 failed.
```

## 2. 根因（先记录后修，诊断过程如实留痕）

初判曾怀疑「tarball 截断」，经核验**推翻**，真实根因如下：

| # | 事实 | 证据 |
|---|---|---|
| R1 | tarball **完整无损**，不是截断文件 | `stat` = 167061596 B（159M）；上游 `wget --spider` `Content-Length: 167061596` 一致；容器内 `xz -t -c <file> >/dev/null` → rc=0。初判「约 1.5G」为对 llvm 源码树解压后体积的误记，压缩包本身即 159M |
| R2 | do_unpack 的 `xz -dc \| tar` 进程被 **SIGKILL** | log.do_unpack 首行 `Killed`，随后 `tar: Unexpected EOF in archive`；是管道 writer 被杀导致 tar 读半途 EOF，非文件损坏 |
| R3 | 构建容器无内存限制，排除容器 OOM | `cat /sys/fs/cgroup/memory.max` = `max`；容器 `MemTotal=129308484 kB`（约 123 GiB）；`docker inspect` NanoCpus/Memory/CpuQuota=0/0/0 |
| R4 | llvm 链来自 dev/prod edition 未裁剪图形特性 | `bitbake -e`：dev/prod 的 `DISTRO_FEATURES` 含 `x11 opengl wayland vulkan`，ci 经 CHG-004 已 remove；mesa→llvm→clang 进入依赖树，llvm-project-source 的 `xz -dc \| tar` 解压到 sysroot 时内存峰值高 |
| R5 | 宿主 shell 自身 cgroup 限 8 GiB，但不是构建容器限制 | 宿主 `/sys/fs/cgroup/memory.max`=8589934592（AGENTS §2.1 明确：宿主 shell cgroup 不代表 Docker daemon）；疑似宿主级 OOM killer 在高并发解压大源码时触发，尚无 dmesg 直接证据，标 `UNVERIFIED` |

## 3. 修复决策与第二次失败

第一次修复：不删 tarball（完整），重试构建。重试越过 llvm do_unpack（证明偶发），但在 `gcc-cross-x86_64 do_compile` 再次失败：

```
build/genautomata ... Killed ; make[1]: *** Error 137 ; ERROR: oe_runmake failed
Tasks Summary: Attempted 2760 of which 2070 didn't need rerun and 1 failed；BUILD_RC=2
```

| # | 事实 | 证据 |
|---|---|---|
| R6 | gcc `genautomata` 被 SIGKILL（137=128+9） | log.do_compile 明确 `Killed` + `Error 137` |
| R7 | dev 独立 sstate 0% 命中，交叉工具链全量重编 | `Sstate summary: Wanted 1495 Local 0 Mirrors 0 Missed 1495 Current 1055 (0% match)` |
| R8 | 构建并发按标称资源拉满 | `BB_NUMBER_THREADS=32`、`PARALLEL_MAKE=-j16`（yp_build_threads 按容器可见内存分级，容器 cgroup memory.max=max） |
| R9 | 真实可用内存低于标称 | 宿主 shell cgroup memory.max=8G；容器内编译在 32×16 并发下连续被 OOM killer 杀 → 嵌套沙箱实际内存不足以支撑全量交叉工具链编译 |

**根因归纳**：标称 32c/128G，但嵌套沙箱真实内存不足以支撑 dev 独立 sstate 下 32×16 并发的交叉工具链全量编译 → 宿主级 OOM 反复杀编译进程。归类 `RESOURCE_PARTIAL`，不伪称 full-quota。

**修复**：用既有 `BB_NUMBER_THREADS` 机制（M0.1.2 资源化，不新引入固定值）在**本次构建**降低并发（仅改 /work/s1build 的本地 conf，不入库、不改 dev.yml）。不改 dev.yml 的 `DISTRO_FEATURES`（CHG-004 裁剪属改 edition 行为，超出 S1 范围）。

## 4. 复验与第三个障碍（prod 构建）

| # | 现象 | 根因 | 修复 |
|---|---|---|---|
| P3 | dev 构建（低并发重试）成功产出 `yp-image-dev-qemux86-64.rootfs-20261127125613.ext4`（152M，manifest 含 gdbserver/perf/strace/trace-cmd/quilt/gdb），但 `kas build` 客户端在 do_image_ext4 后卡住不写 BUILD_RC | 嵌套沙箱 bitbake server/client 收尾通信卡住；产物已在 `deploy-*-image-complete/` 完整落盘 | 终止卡住的客户端；以已落盘的 ext4 + manifest 为验收证据，不冒充「BUILD_RC=0」 |
| P4 | prod 构建在同一 build 目录失败：`basehash value changed ... metadata is not deterministic` + `No such task: do_rm_work`（quilt-native） | dev 用 `INHERIT:remove = " rm_work"`、prod 用 `INHERIT += "rm_work"`，同一 build 目录/datastore 切换 edition 导致任务哈希不稳定 | 用**全新独立 build 目录** `/work/s1build-prod` 构建 prod，不复用 dev 的 datastore |
