## 1. 变更内容

### 1.1 `kas/base.yml` + `yp-concurrency.bbclass`：并发改为 CPU + cgroup 内存分级（ISS-038）

- 变更前：`BB_NUMBER_THREADS = "${@oe.utils.cpu_count()}"`、`PARALLEL_MAKE = "-j ${@oe.utils.cpu_count() // 2}"`（只按 CPU，低内存高 CPU 有 OOM 风险）。
- 变更后新增 bitbake python 函数（放在 `meta-yp-distro/classes/yp-concurrency.bbclass`，由 base.yml 的 `INHERIT += "yp-concurrency"` 引入；**bitbake 的 local.conf ConfHandler 不支持多行 `def`，实测构建 ParseError，故按 ISS-040 移入 .bbclass**，语义与提示词参考实现一致）：
  - `yp_mem_bytes(d)`：读 `/sys/fs/cgroup/memory.max`（v2）→ `/sys/fs/cgroup/memory/memory.limit_in_bytes`（v1）→ 回退 `/proc/meminfo MemTotal`；`max` 或 `>=1<<60` 视为无效继续回退。Docker `--memory` 不改写 `/proc/meminfo`，故必须先读 cgroup。
  - `yp_build_threads(d)`：`cpus = oe.utils.cpu_count() or os.cpu_count() or 1`；`mem_gb = yp_mem_bytes(d)//GiB`；按 standard(32/≥120)→32、mid(16/≥32)→min(16,cpus)、small(8/≥16)→min(8,cpus)、legacy→min(4,cpus)，`max(1,n)`。
- `kas/base.yml`：`INHERIT += "yp-concurrency"`、`BB_NUMBER_THREADS = "${@yp_build_threads(d)}"`、`PARALLEL_MAKE = "-j ${@max(1, int(d.getVar('BB_NUMBER_THREADS')) // 2)}"`（不出现 `-j 0`）；函数在 `.bbclass` 内定义并经 INHERIT 引入（ISS-040）。
- 不回退 `os.environ.get`（ISS-037）；`YP_BUILD_THREADS`/`YP_PARALLEL_MAKE` 不再是控制变量（ISS-039）；base.yml 不含这些 env 字面串。
- 不改 `DL_DIR`/`SSTATE_DIR`/`BB_HASHSERVE`/`BB_HASHSERVE_DB_DIR`/`BB_SERVER_TIMEOUT` 等其他契约。

### 1.2 `scripts/build/threads.sh`：只读 daemon 级诊断（ISS-039）

- 删除 env 覆盖逻辑（`YP_BUILD_THREADS`/`YP_PARALLEL_MAKE` 的正整数校验与覆盖）与 `export` 输出。
- 输出：`RESOURCE_TIER` / `RESOURCE_CORES` / `RESOURCE_MEM_GB` / `SUGGEST_BUILD_THREADS` / `SUGGEST_PARALLEL_MAKE`。
- 分级表与 base.yml 语义一致（standard/mid/small/legacy，`min`/`max(1,..)`）；仍读 docker daemon NCPU/MemTotal，daemon 不可用 exit 1。
- 注释明确：daemon 级诊断、非 bitbake 控制通道；实际值以容器内 `bitbake-getvar` 为准，负向容器下诊断值与实际值可能不同。

## 2. 为什么要改

- B2 决策：并发必须同时按 CPU 和内存分级，避免只按 CPU 翻倍在 8 GB 容器 OOM。
- C2 决策：`threads.sh` 只做 daemon 级诊断，不再当 bitbake 控制通道（ISS-037 已证 env 注入无效，ISS-039 指出文档误导）。
- 不改 M0 判据 1–8、不移动 `m0.1`/`m0.1.1` tag。

## 3. 影响面

| 维度 | 影响 |
|---|---|
| 标准机 32c/128G | 结果不变（32/-j16），bitbake-getvar 实测确认 |
| 中低配内存不足 | 自动降级（16/16→8/-j4、32/64→16/-j8、64/4→4/-j2），消除 OOM 风险 |
| 构建产物 | 不变（同一 prod edition、同一 ext4） |
| 缓存/发布契约 | 不改 DL_DIR/SSTATE_DIR/hashserv/分片/manifest |
| 门禁 | gate/vars 仍绿；G6/负向断言防回归 |

## 4. 回滚方式

`git revert` 本提交恢复纯 CPU 表达式与旧文档；但会重现高 CPU 低内存 OOM 风险（ISS-038）与 doc 误导（ISS-039）。恢复 `os.environ.get` 会重现 getvar=4（ISS-037），不建议。

## 5. 验证方式

见 `docs/m0.1/reviews/RV-021.md`：threads.sh 诊断输出、分级逻辑复核、容器 fresh `bitbake-getvar` 32/-j16、负向容器 NEGATIVE_ONLY getvar 矩阵、缓存 prod 构建、CPU/内存采样、CI run id。4c/8G 全冷构建按用户要求不做（D2）。
