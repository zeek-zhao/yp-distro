## 1. 变更内容

- 变更前：`cache-payload` 制品没有任何生产者；`publish-cache-slices` 下载必然失败（run `45601074345`）。
- 变更后：

| 契约项 | 新值 |
|---|---|
| 生产 job | `prepare-cache-payload`，作为 `publish-cache-slices` 的 `needs` 前置 |
| 载荷源 | release tag `m0-s5-payload-sample` 中的资产 `cache-payload-sample.tar.gz` |
| 资产内容 | 顶层 `downloads/` 与 `sstate/`，文件抽样自 M0 S5 真实构建缓存（`/tmp/yp-dl`、`/tmp/yp-st`），非伪造、非空目录 |
| 文件名处理 | 上传制品前把文件名中的 `:` 替换为 `_`（ISS-018：`upload-artifact@v4` 禁止冒号），内容与目录结构不变 |
| 制品落库 | `actions/upload-artifact@v4`，名称 `cache-payload`（与 CHG-008 消费端契约一致） |
| 消费端 | 不变：`actions/download-artifact@v4` → `runner.temp/s5-payload` → `Verify S5 payload` 校验后 pack/split/publish |
| 资产定位 | 按 tag + 资产名查询，不在仓库中写入 asset id 或 token |

## 2. 为什么要改

- ISS-016 的直接原因 A 是「`cache-payload` 制品不存在」。CHG-008 只规定了消费端契约，没有生产者。
- 完整 S5 缓存为 5.8 GiB + 4.7 GiB，超出 GitHub 发布资产与制品的实用体积；按可上传体积抽样真实构建产物，用于证明「制品交接 → pack → split → push → inspect digest」全链路可用。
- 抽样不改变 `scripts/cache/*` 的阈值与切分逻辑；本地 T5 已用 4 片证明超限切分与完整性校验，本变更只补齐发布端到端。

| 外部状态 | 新增一个 release tag 与其资产；不新建 PR，不改默认分支 |

## 4. 回滚方式

- 回滚命令：`git revert <本提交 SHA>`；删除 release tag `m0-s5-payload-sample`。
- 回滚后如何验证：`git grep 'prepare-cache-payload'` 无命中；发布 run 回到「缺载荷即失败」的诚实路径。
