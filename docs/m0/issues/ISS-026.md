## 1. 现象（只写观察到的事实）

- 观察到的输出／现象：`fetch-cache.sh` 的 release 模式仅在 `count == M_COUNT && layout == two-stage` 时才把全部分片 `cat` 重组为 archive；`--parts <n>`（n<总数）会落到 else 分支，把第一片 `$A0_NAME` 当作整个 tar 解包。该片只是 1,572,864,000 B 的分段，不是有效 tar。
- 影响范围：使用 `--parts` 从 two-stage release 取部分分片的场景；本轮用全量 8 分片（count==M_COUNT），未触发。

sed -n '186,190p;207,210p;233,237p' scripts/cache/fetch-cache.sh
# if [ "$count" -eq "$M_COUNT" ] && [ "$M_LAYOUT" = "two-stage" ]; then : > archive; cat parts...
# else eval "n=\$A0_NAME"; archive="$WORK/$n"; note "SHA256_OK ... (single asset)"

- 期望结果：`--parts` 若不支持 two-stage 重组，应明确报错并说明只支持 sample/direct，而非静默把单片当整 tar。
- 实际结果：静默取单片当 archive，后续解包必失败且错误信息误导。
- 首次出现于：T3 实现；本轮 HEAD `88246d0` 代码走查确认。

## 3. 根因分析（Analyzed 阶段填写）

- 直接原因：重组分支条件绑定 `count == M_COUNT`，`--parts` 绕过后无重组逻辑。
- 根本原因：`--parts` 选项的语义未覆盖 two-stage 布局。
