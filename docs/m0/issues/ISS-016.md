## 1. 现象（只写观察到的事实）

- Push `316b9fa`（含 `kas/yp.yml` 变更，命中 CHG-007 的 `kas/**` path）成功触发 M0 publish run `45601074345`（`event=push`、`head_sha=316b9fa`、`conclusion=failure`）：https://github.com/zeek-zhao/yp-distro/actions/runs/45601074345
- 同次 push 的 gate run `45601074218` → `success`，证明 push 触发可用且门禁已修好。
- publish run 三个 job 均 `failure`：

| job | 观察到的失败原因（GitHub job 页面公开可见文本） |
|---|---|
| `publish-cache-slices` | `::error::S5 cache-payload 制品下载失败（outcome=failure）；请先由 S5 上传名为 cache-payload 的制品（含 downloads/ 与 sstate/）` |
| `publish-builder` | `ERROR: failed to build: failed to solve: failed to push ghcr.io/zeek-zhao/yp-builder:wrynose-m0: denied: permission_denied: write_package` |
| `publish-cache` | `ERROR: failed to build: failed to solve: failed to push ghcr.io/zeek-zhao/yp-cache:wrynose-m0: denied: permission_denied: write_package` |

- 没有产生任何分片 tag 的真实 digest；job summary 中的 digest 行为空（符合 T3「失败即停」设计，未出现 `push-ok` 假绿）。

- 期望结果：发布端到端成功，填 run URL 与 digest。
- 实际结果：三个 job 全红；无 digest；两类原因分别是「缺 S5 制品载荷」与「GITHUB_TOKEN 无包写权限」。
- 首次出现于：run `45601074345` / 提交 `316b9fa`。

## 3. 根因分析

- 直接原因 A：`cache-payload` 制品不存在（仓库没有 S5 上传步骤）；这是 CHG-008 明确要求的失败路径，**不是脚本缺陷**。
- 直接原因 B：workflow 已声明 `permissions: packages: write`，但 Actions 注入的 `GITHUB_TOKEN` 实际被仓库/GHCR 侧拒绝 `write_package`；此前成功推送用的是用户独立 TOKEN（ISS-004/005），并非 GITHUB_TOKEN。
- 根本原因：方案 A 的孤立分支上，发布链路同时缺「S5 制品上传」与「可用的 GITHUB_TOKEN 包写权限」两个外部前提；CHG-007 只解决触发，CHG-008 只解决诚实失败，不能凭空产生前提。
- 排除过的假设：不是 push 未触发（run 已存在且 gate 同 push 成功）；不是 `docker/build-push-action` 语法错误（builder/cache 均到达 push 阶段并被权限拒绝）。
