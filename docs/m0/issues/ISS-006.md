# YP-M0-ISS-006 · cache 镜像数据卷属主与 builder 非 root 约束冲突

| 字段 | 值 |
|---|---|
| 编号 | YP-M0-ISS-006 |
| 状态 | Closed（已修复并验证） |
| 严重度 | 中（阻断两个官方镜像直接协同，但不影响各自单独使用） |
| 发现阶段 | S7 匿名拉取后端到端组合验证 |
| 关联 | DES-006、DES-007、B-04、B-08 |
| 发现人 / 日期 | zeek.zhao / 2026-11-24 |

## 1. 现象

两个镜像均从公共 GHCR 匿名拉取成功后，执行端到端组合：

```
docker run -d --name yp-cache-vol ghcr.io/zeek-zhao/yp-cache:wrynose-m0 sleep 3600
docker run --rm --volumes-from yp-cache-vol ghcr.io/zeek-zhao/yp-builder:wrynose-m0 whoami
```

builder 的 entrypoint 拒绝启动：

```
ERROR: /work/downloads 属主 UID=0，与 jenkins UID=1000 不一致。
combine_exit=1
```

## 2. 根因

`docker/cache.Dockerfile` 用 `RUN mkdir -p /work/downloads /work/sstate` 创建卷目录，未 chown，默认属主 `0:0`。builder 镜像的 entrypoint 强制校验挂载卷属主为 jenkins（UID 1000，B-04），两者不一致。属主冲突在各自单独使用时被掩盖（builder 单独用 host 目录已正确 chown），仅在 `--volumes-from` 组合时暴露。

## 3. 修复

在 cache.Dockerfile 创建目录后按可配 UID/GID chown（默认对齐 builder 的 jenkins 1000:1000）：

```dockerfile
ARG CACHE_UID=1000
ARG CACHE_GID=1000
RUN mkdir -p /work/downloads /work/sstate /work/cache \
    && chown -R "${CACHE_UID}:${CACHE_GID}" /work/downloads /work/sstate
```

## 4. 验证证据（真实输出）

- 修复版本地构建：成功，`naming to docker.io/library/yp-cache:fix-test`
- 卷属主：`1000:1000 /work/downloads`、`1000:1000 /work/sstate`
- 端到端组合：`user=jenkins`、`1000:1000 /work/downloads`、`WRITE OK`、`combine_exit=0`
- 重新推送公共 GHCR（新 digest `sha256:1eaf38f57af7ca230831e357255f7b961da7ed80d48e3a8d5019fd9e300abd03`）后登出并匿名拉取：`Digest: sha256:1eaf38f5...`、`Status: Downloaded newer image`；
- 匿名拉取版卷属主：`1000:1000 /work/downloads`、`1000:1000 /work/sstate`；
- 最终端到端（两个镜像均匿名拉取）：`user=jenkins`、`kas 5.5`、`cache+builder WRITE OK`、`FINAL_EXIT=0`。

## 5. 关闭

- 关闭条件：修复版推送到公共 GHCR，匿名拉取后端到端组合通过。
- 关闭人 / 日期：zeek.zhao / 2026-11-24
- **下次如何避免**：数据卷镜像的目录属主必须与消费者镜像的运行 UID 对齐；设计阶段就把 UID/GID 作为跨镜像契约写入 ADR，并在组合场景（而非仅单独场景）做验收。
