## 1. 现象

首次 `bash scripts/gate.sh` 实跑 `GATE_FAIL`（应为 PASS），两处误报：

```text
[FAIL] G2 源码范围出现非 threshold.conf 的阈值定义:
scripts/gate.sh:25:... grep -rn "8589934592\|8G" ...
scripts/check-vars.sh:33:... 'SLICE_MAX_BYTES|...|SLICE_MAX_BYTES=8589934592'
.github/workflows/m0-gate.yml:2:# ... 8GB ...
[FAIL] G5 acceptance 缺判据  6 / 1 / 2 / 3 / 4 / 5 / 7（带前导空格）
[FAIL] G5 未知验收行取值: BB_HASHSERVE" kas/ ...
```

## 2. 根因

- **G2 自指**：门禁脚本自身的 grep 模式字符串含 `8589934592`，workflow 注释含 `8GB`——这些是"检查逻辑"而非"阈值定义"，被自身 grep 命中。
- **G5 解析**：traceability 证据列含反引号与 `|`（如 `` `grep "SSTATE_MIRRORS\|BB_HASHSERVE"` ``），`awk -F'|'` 把单元格内 `\|` 当分隔符导致列错位；且 `$6` 取值带前导空格未 trim，`grep -E "^\| $n \|"` 因双空格不匹配。

## 3. 修复

- G2：排除 gate.sh / check-vars.sh 自身、排除注释行（`#` 开头或行内注释），只断言"非注释的赋值行"（`SLICE_MAX_BYTES=`/`8G` 作为配置值出现）。
- G5：改用「按判据号精确匹配」——从 traceability 每行提取 `判据\s*[0-9]`（正则，容错空格），trim 后与 acceptance 的 `| N |` 行比对；跳过非判据取值（容器实跑等）不报 FAIL。

## 4. 验证证据（修复后实跑）

```text
--- G2 阈值唯一性 ---
  [PASS] G2 源码范围仅 threshold.conf 定义阈值（已排除门禁脚本自身与注释）
  [PASS] G2 docker/cache-meta.json 与 gen-meta 生成值一致（生成产物）
--- G5 文档一致性 (traceability -> acceptance) ---
  [PASS] G5 traceability 引用的判据在 acceptance 均存在，且判据 1-8 均被引用
===== GATE RESULT =====
GATE_PASS
GATE_EXIT=0
```

判据 8 检出样例仍生效：故意改 `BB_NUMBER_THREADS` 4→8 → `DRIFT` + exit 1 → 还原 → `VARS_OK`（见 RV-009 §验收输出）。

## 5. 关闭

- 关闭条件：`bash scripts/gate.sh` 输出 GATE_PASS exit 0；判据 8 检出样例仍生效——**均达成**。
- 关闭人 / 日期：zeek.zhao / 2026-11-25
- **下次如何避免**：门禁规则若用 grep 扫描源码，必须先排除门禁脚本自身与注释行（自指误报）；解析 markdown 表格时不能用朴素 `-F'|'`（单元格内可能含转义 `|`），应按语义正则提取而非按列切分。
