## 1. 现象（只写观察到的事实）

- 观察到的输出／现象：`docker/cache-provenance.json`、`docker/cache-meta.json` 中 `payload_sha256=1c8126d4b1c57d5dc5a4f772617cd74dacbeab475d79e8ce2ee49bbcea1be624` 配 `payload_bytes=11153397760`。而本轮 §6 dry-run 打印的期望值为 `EXPECTED_ARCHIVE ... sha256=1c8126d4… bytes=11153387520`，`manifests/cache-full.release.json` 的 `expected_bytes=11153387520`。两者相差 10,240 B。
- 影响范围： provenance/元数据一致性；文档事实口径。不影响 release 分片本身（字节数/hash 以 release 实际资产为准）。

## 2. 复现

```bash
# HEAD 88246d0
grep -n 'payload_bytes' docker/cache-provenance.json docker/cache-meta.json
# 11153397760
bash scripts/cache/fetch-cache.sh --mode release --dry-run --dest-parent . --work ./cache-work --release-tag m0-s5-payload-full | grep EXPECTED_ARCHIVE
# EXPECTED_ARCHIVE name=cache-full.tar sha256=1c8126d4… bytes=11153387520
grep -n expected_bytes manifests/cache-full.release.json   # 11153387520
```

- 期望结果：`payload_sha256=1c8126d4…` 对应 `payload_bytes=11153387520`（release 8 分片之和）。
- 实际结果：对应 `11153397760`（该值是 GHCR 全量切片源 tar `a8870b50…` 的大小，与 `1c8126d4…` 不是同一对象，见 runbook §2 / RV-013 事实核对第 3 条）。
- 首次出现于：CHG-013 / T5 引入静态 provenance 时；本轮 HEAD `88246d0` 实测复现。

## 3. 根因分析（Analyzed 阶段填写）

- 直接原因：静态 provenance 文件把两个不同 tar 的 hash 与大小交叉配对（`1c8126d4` 来自 release 重组 tar，`11153397760` 来自 GHCR 切片源 tar `a8870b50`）。
- 根本原因：CHG-012/CHG-013 阶段 release 重组 tar 与 GHCR 切片源 tar 是两个对象、相差 10,240 B，填写 provenance 时未区分。
- 排除过的假设及排除依据：不是 release 资产错（GitHub API 实测 8 分片之和 = 11,153,387,520 B，dry-run 一致）；不是 dry-run 脚本错（manifest 期望值正确）。
