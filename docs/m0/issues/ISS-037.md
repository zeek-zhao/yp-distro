# YP-M0-ISS-037 · kas 隔离 bitbake server 环境变量导致并发注入失效

| 项 | 值 |
|---|---|
| 文档编号 | YP-M0-ISS-037 |
| 状态 | Resolved（改 `oe.utils.cpu_count()` 动态分级，实测 32/-j16 生效） |
| 提出日期 | 2026-11-26 |
| 关联 | YP-M0-CHG-021 / YP-M0.1-RV-020；AI-009 §2.1/§2.2；分支 `feat-m0.1-evidence` |
| 严重度 | P2（阻断 R3「32 线程真生效」，但不影响构建成功与产物） |

## 1. 现象

按 AI-009 §2.2 在 `kas/base.yml` 写 `BB_NUMBER_THREADS = "${@os.environ.get('YP_BUILD_THREADS', '4')}"`，并在 `docker run -e YP_BUILD_THREADS=32 YP_PARALLEL_MAKE='-j 16'` 注入、`threads.sh` 输出 standard/32/-j16。但 `bitbake-getvar --value BB_NUMBER_THREADS` / `PARALLEL_MAKE` 在真实构建容器内**始终返回 4 / -j 2**，未达 32/-j16。

## 2. 诊断过程（原始证据）

| 尝试 | 结果 |
|---|---|
| `docker run -e YP_BUILD_THREADS=32` + `${@...}` | getvar=4 |
| `kas/base.yml` 加 `env:` 段（默认 4 / 32 / null） | getvar=4，且 `bitbake-getvar YP_BUILD_THREADS` 显示变量未定义或 4 |
| 改 `??=` / `?=` 定义 + `${YP_BUILD_THREADS}` 引用 | getvar=4 |
| `docker exec -e BB_NUMBER_THREADS=32`（bitbake 原生 passthrough 变量） | getvar=4 |
| `kas shell -E --preserve-env`（伪 tty） | getvar=4 |
| `kas build ... -- BB_NUMBER_THREADS=32`（extra bitbake args） | 拼成 `bitbake -c build BB_NUMBER_THREADS=32 ...` → `Nothing PROVIDES 'BB_NUMBER_THREADS=32'`（变量被当 target） |
| `pkill bitbake-server` 后新 server + 当前环境 | getvar 仍 4；`kas shell -c python3` 内 `os.environ.get('YP_BUILD_THREADS')`=None，而 shell 层 `echo $YP_BUILD_THREADS`=32 |

根因：**kas 5.5 在启动 bitbake server 时重建了进程环境（白名单）**，`YP_BUILD_THREADS` 等自定义变量不进 bitbake server 的 `os.environ`；`${@os.environ.get(...)}` 在 datastore 求值时恒取默认 4。kas `env:` 段虽把变量加入 `BB_ENV_PASSTHROUGH_ADDITIONS`，但在本版本的 `kas shell`/`kas build` 路径未把宿主值注入 datastore。这是 kas/bitbake 版本行为，非配置笔误。

## 3. 修复

改用 bitbake 原生动态函数，不依赖任何环境传递：

```bitbake
BB_NUMBER_THREADS = "${@oe.utils.cpu_count()}"
PARALLEL_MAKE = "-j ${@oe.utils.cpu_count() // 2}"
```

- `oe.utils.cpu_count()` 在 bitbake datastore 求值时读取进程可见 CPU（容器内 = Docker daemon 可见 = 32）→ `BB_NUMBER_THREADS=32`、`PARALLEL_MAKE=-j 16`。
- 4c/8GB 机自动得 4/-j2（ISS-011 历史回退保留），与 `threads.sh` 分级表一致，无需写死。
- 修复后 fresh server `bitbake-getvar --value` 实测 = 32 / -j 16（RV-020 §2）。

## 4. 影响面与取舍

- 偏离 AI-009 §2.2 字面写法（`os.environ.get`），但**达成其目标**（按资源分级、env 覆盖语义由 cpu_count 自动实现、默认回退保留）；记为文档与代码对齐（硬边界 6），不弱化 `AGENTS.md` §2.1 与 `RESOURCE_PARTIAL`。
- `threads.sh` 保留为只读分级诊断工具（R1 验证 + verify-env SUGGEST），分级表与 cpu_count 结果一致；不再作为 bitbake 变量的传递通道。
- 不写死 32/-j16（gate G6 + check-vars 断言防回归）。

## 5. 回滚

恢复 `os.environ.get` 写法会重现 getvar=4（R3 失败）；不建议。

## 6. 后续更正（M0.1.2 / ISS-039）

M0.1.2 已进一步移除 M0.1.1 遗留的无效 env 导出：`threads.sh` 不再输出 `export YP_BUILD_THREADS/YP_PARALLEL_MAKE`（改只读 `SUGGEST_*` daemon 诊断），runbook/测试提示词不再用 `eval`/`export` 当控制通道，详见 ISS-039 / CHG-022 / RV-021。本 issue 历史结论不改。
