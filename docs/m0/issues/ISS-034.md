## 1. 现象（只写观察到的事实）

- 观察到的输出／现象：README 目标段与「三步上手」开头、runbook §1 均写「宿主机只装 Docker/只需要 Docker」；但 `git clone` 需 `git`，`fetch-cache.sh` 硬依赖 `python3`（`command -v python3` 与 token JSON 解析），下载需 `curl`、解包需 `tar`、校验需 `sha256sum`。`verify-env.sh` 目前只在 registry 段检查 `curl`，缺 `python3` 时 token 解析得空，报 `REGISTRY 无法取得 ghcr.io 匿名 token（网络/代理/401？）`（line 136），被误读成网络/401，而非缺依赖。
- 影响范围：新机前置条件说明与故障判定；缺 python3 的机器会走错排障路径（§5.3 GHCR 401）。

## 2. 复现

```bash
grep -rn "只装 Docker\|只需要 Docker" README.md docs/runbook-new-machine.md
# README.md:7 / README.md:39 / docs/runbook-new-machine.md:11
grep -n "command -v python3\|python3 -c" scripts/cache/fetch-cache.sh | head
grep -n "无法取得 ghcr.io 匿名 token" scripts/verify-env.sh
# 136: fail "REGISTRY 无法取得 ghcr.io 匿名 token（网络/代理/401？见 runbook §5.3）"
```

- 期望结果：文档如实列出宿主依赖；verify-env 在 registry 探测前检查 `git/bash/python3/curl/tar/sha256sum`，缺 python3 首行报 `FAIL DEP_MISSING python3`。
- 实际结果：文档称只装 Docker；verify-env 缺依赖检查，误导为 registry 401。
- 首次出现于：提交 `1d1ddb6`（及更早）。

## 3. 根因分析（Analyzed 阶段填写）

- 直接原因：早期设计只强调「宿主机无 kas，构建在容器」，把「只装 Docker」当成卖点写进文档，忽略 clone/fetch/verify 的宿主工具依赖。
- 根本原因：前置条件清单未随 fetch/verify 脚本的依赖演进更新；verify-env 的失败归因没有区分「缺工具」与「网络失败」。
- 排除过的假设及排除依据：容器内构建确实不需宿主 kas/bitbake，这条仍成立；错在把「不需 kas」写成「只装 Docker」。
