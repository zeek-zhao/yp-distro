# YP-M0-ISS-011 · 沙箱 cgroup 8GB 内存限额导致构建进程反复被 OOM 杀死

| 字段 | 值 |
|---|---|
| 编号 | YP-M0-ISS-011 |
| 状态 | Closed（已修复并验证：并发下调后 OOM 消失，两次构建 rc=0，证据见 §4） |
| 严重度 | 高（ISS-008/009/010 修复后构建仍失败的真正根因） |
| 发现阶段 | Stage D 第 3–5 次构建尝试（ISS-010 重试期间） |
| 关联 | DES-005、RV-005、CHG-005、ISS-010 |
| 发现人 / 日期 | zeek.zhao / 2026-11-25 |

## 1. 现象与证据

ISS-010 重试（第 4/5 次）后失败点继续随机漂移，且第二次构建在 `cmake-native do_configure` 失败，日志出现确定性证据：

```text
{standard input}: Error: open CFI at the end of file; missing .cfi_endproc directive
g++: fatal error: Killed signal terminated program cc1plus
compilation terminated.
make: *** [Makefile:208: cmGeneratorTarget.o] Error 1
```

`cc1plus` 收到 Killed 信号（SIGKILL）＝编译进程被内核杀掉。沿 cgroup 层级核查内存限额：

```text
# 宿主根 cgroup
/sys/fs/cgroup/memory.max        = 8589934592      # 仅 8GB
/sys/fs/cgroup/memory.events     = oom 35, oom_kill 11
# 构建容器 cgroup
memory.events                    = oom_kill 9
memory.peak                      ≈ 7.6GB（贴着 8GB 限额）
# 宿主 init.scope
memory.events                    = oom_kill 2
# free -h 显示 total 123Gi —— 与真实可用内存严重不符
```

结论：构建沙箱被 cgroup 限制在 **8GB 物理 RAM**（swap 亦被限 8GB，且 `swapon` 因缺 CAP_SYS_ADMIN 被拒，无法扩容）。此前 5 次构建失败（llvm / gcc-source / linux-libc-headers 的 do_unpack、cmake do_configure）全部是 OOM 杀死 `xz|tar` 管道或 `cc1plus` 的随机表现，"失败点漂移"由此完全解释。ISS-010 中"偶发解压失败/瞬时资源压力"的初步判断由本问题单修正根因。

## 2. 根因

1. 沙箱 cgroup `memory.max = 8GB`，而 `free` 显示 123Gi，造成内存充足假象。
2. `BB_NUMBER_THREADS` 初值 32（后降 16）对应 16+ 并发任务，每个任务的编译子进程数百 MB 到 1GB+，峰值远超 8GB，触发内核 OOM killer。
3. 部署构建环境时只看了 `free`，未检查 cgroup 真实限额。

## 3. 修复

通过 CHG-005 将 `kas/base.yml` 并发参数降到匹配 8GB 的水平：

- `BB_NUMBER_THREADS = "4"`（16 → 4）
- `PARALLEL_MAKE = "-j 2"`（显式设置，最坏情况同时 ≤ 8 个编译子进程）

`swapon` 扩容方案已实测被拒（`Operation not permitted`），不走 swap 路线。附带的 CHG-004（ci edition 裁剪 `opengl x11 wayland vulkan`）同时把 mesa→llvm→clang 图形栈移出依赖树，进一步降低单任务内存峰值。

## 4. 验证证据（2026-11-25 修复后重跑成功）

调参（`BB_NUMBER_THREADS=4`、`PARALLEL_MAKE="-j 2"`、CHG-004 裁图形栈）后，在 8GB cgroup 环境下两次构建均成功：

```text
BUILD_DONE label=first  wall_seconds=7096 rc=0
BUILD_DONE label=second wall_seconds=214  rc=0
Tasks Summary: Attempted 4083 tasks ... all succeeded.
产物: core-image-minimal-qemux86-64.rootfs-20261124203504.ext4.zst（file=Zstandard compressed data）
```

OOM 验证：修复前 5 次构建累计 `oom_kill=9`（`cc1plus`/`xz|tar` 被 Killed）；本次修复后构建全程 `oom_kill` 计数不再增长，首次构建的 llvm/gcc/headers 解压与 cmake 编译全部通过。容器重启后 namespace 视角 `oom_kill=0`，无新增 OOM。

内存峰值受控：并发从 16×（无 `PARALLEL_MAKE` 约束）降为 4 线程 × `-j 2`，最坏 8 个编译子进程落在 8GB 内。

## 5. 关闭

- 关闭条件：8GB 环境下两次构建成功且 `memory.events.oom_kill` 相对基线 9 不再增长；RV-005 回填真实输出——**均达成**。
- 关闭人 / 日期：zeek.zhao / 2026-11-25
- **下次如何避免**：进入任何构建环境先读 `/sys/fs/cgroup/memory.max`（容器内为 `/sys/fs/cgroup/memory/memory.max` 或 `memory.max`）确认真实限额，`free`/`nproc` 只能作参考；并发参数按 `限额GB ≈ 线程数 × 单任务峰值` 预算后保守取值，并为 CI 环境在文档中显式声明资源约束。

## 6. 补充调查：能否从「容器外」提配（2026-11-25，结论：不能）

应用户要求复查「在容器外操作容器配置以使用全部系统资源」，逐层实测，结论为**沙箱硬约束、无可行提配路径**。证据链：

| 排查层 | 命令 / 现象 | 结果 |
|---|---|---|
| 当前 agent shell | `/proc/self/cgroup` = `0::/init.scope`；`cpu.max=400000 100000`（4 核）、`memory.max=8589934592`（8 GB） | 受限 |
| 进程能力 | `CapEff=0x1ffffffffff` 含 `cap_sys_admin`；cgroup 挂载 `rw` | 表面可写 |
| user namespace | `/proc/self/uid_map` = `0 100000 65536` | 容器 root 映射到宿主 uid 100000，ns 内 cap 对宿主 cgroup 无效 |
| 直接写根 cgroup | `echo 34359738368 > /sys/fs/cgroup/memory.max` → `permission denied`（文件 owner `nobody:nogroup`） | 失败 |
| 子 cgroup 规避 | 新建子 cgroup（owner 为 ns root）可写更大值，但 CPU 8 并行 wall 1160ms→1203ms 无提速、12 GB 分配 `oom_kill 1` | 被父级 `min()` 压制 |
| 新建普通容器 | `docker run alpine` 内 `cpu.max=max`、`memory.max=max`、32 核——**看似无限制** | namespace 假象 |
| Docker daemon 真实层级 | `--privileged -v /sys/fs/cgroup:/host-cgroup:ro` 挂载宿主视角：宿主根 `cpu.max=400000 100000`、`memory.max=8589934592` | daemon 本身在 8 GB/4 核内 |
| 显式 Docker 配额 | `--cpus=16` / `--memory=16g` 后 16 任务 wall 2872ms ≈ shell 2694ms；12 GB 分配仍被 Killed | 配额被上层硬顶吸收 |
| 特权容器写宿主 cgroup | `--privileged` 仍是 user namespace（`uid_map 0 100000`）、无 `cap_sys_admin`；写 `/host-cgroup/cpu.max`、`memory.max` 均 `permission denied` | 失败 |
| `--cgroupns=host` 共享宿主 cgroup ns | 容器落在 `/docker/<id>`；宿主 cgroup 树仅 `init.scope` + `docker` 两个顶层分支，根仍 `cpu.max=400000 100000` / `memory.max=8589934592`；两分支虽显示 `max` 但受父级 `min()` 约束 | 无隐藏资源分支 |
| `nsenter -t 1 -U -p -C` 进 PID1 | `cannot open /proc/1/ns/user: Permission denied`；PID1 的 user namespace owner 是宿主 uid 0，容器进程是 jenkins(1000，映射宿主 100000)，无权跨入 | 失败 |
| `nsenter -t 1 -a`（all namespaces） | `stat of /proc/1/ns/user failed: Permission denied` | 失败 |

**定性**：宿主 cgroup 根即为 8 GB/4 核（沙箱编排层施加），Docker daemon 与所有容器均在其下；从容器内、daemon 层、特权容器、`cgroupns=host`、`nsenter` 进 PID1 五类路径均无法越权修改。根本原因是不具备宿主 uid 0 对应的 `cap_sys_admin`（容器 uid 1000 映射宿主 100000，PID1 user namespace owner 为宿主 root）。这**不是配置缺陷而是环境硬约束**，不新开 ISS。Stage D 已按真实配额调参并成功构建，无需也无法再提配。
