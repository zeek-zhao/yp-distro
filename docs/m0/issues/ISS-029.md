## 1. 现象（只写观察到的事实）

- 观察到的输出／现象：本轮全量 release 归档 `cache-full.tar` 顶层实际为 `downloads/ sstate/ yp-dl/ yp-st/`（另有内层），`fetch-cache.sh` 识别为 `mode=direct`；而 runbook §4 / RV-013 事实核对第 1 条称顶层为 `./`、`./downloads.tar`、`./sstate.tar`（two-stage）。prompt §6 第 4 点期望 `STRUCT_OK mode=two-stage`。
- 影响范围：文档事实口径；不影响解包正确性——`STRUCT_OK downloads=1288 sstate=6945` 与 provenance 期望一致，`UNPACK_OK`、`FETCH_OK`，后续两卷构建成功。

## 2. 复现

```bash
tar -tf cache-work/cache-full.tar | sed 's#^\./##' | cut -d/ -f1 | sort -u
# downloads
# sstate
# yp-dl
# yp-st
grep -a STRUCT_OK /root/.codebuddy/artifact/2f8a7d30-9c21-4f0b-1d80-90e449221000/fetch.log
# STRUCT_OK mode=direct downloads=1288 sstate=6945
```

- 期望结果：按 runbook §4，顶层应为 `downloads.tar` + `sstate.tar`（two-stage）。
- 实际结果：顶层为卷目录直铺（`direct`），脚本自动识别并正确解包。
- 首次出现于：本轮 HEAD `88246d0` 实跑发现；发布产物本身的布局历史如此。

## 3. 根因分析（Analyzed 阶段填写）

- 直接原因：发布端 `pack.sh` 当前产出 direct 布局（或两层归档被再打包为 direct），而 runbook §4 记录的是早期 two-stage 观察。
- 根本原因：文档记录的布局与实际发布归档未持续对齐；`fetch-cache.sh` 的 `unpack_archive` 同时支持两种布局，故功能不受影响。
