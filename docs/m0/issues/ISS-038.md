# YP-M0-ISS-038 · 并发只按 CPU 不按内存，8GB 容器有 OOM 风险且与 threads.sh 诊断不一致

| 项 | 值 |
|---|---|
| 文档编号 | YP-M0-ISS-038 |
| 状态 | Resolved（改 `yp_build_threads(d)` 按 CPU + cgroup 内存分级，实测 32c/123GiB→32/-j16） |
| 提出日期 | 2026-11-27 |
| 关联 | YP-M0-CHG-022 / YP-M0.1-RV-021；AI-010 §2.1/§2.2；分支 `feat-m0.1.2-resource-fallback` |
| 严重度 | P2（低内存高 CPU 配置下并发过高可 OOM；标准机不受影响） |

## 1. 现象

M0.1.1（ISS-037 修复后）`kas/base.yml` 用：

```bitbake
BB_NUMBER_THREADS = "${@oe.utils.cpu_count()}"
PARALLEL_MAKE = "-j ${@oe.utils.cpu_count() // 2}"
```

只按可见 CPU 分级。问题：

- **只按 CPU 翻倍，不看内存**：一个 `--cpuset-cpus=0-63 --memory=8g` 的容器会算出 64/-j32，8 GB 内存下必然 OOM；违背 ISS-011 的 8 GB 回退 4/-j2 意图。
- **与 threads.sh 诊断不一致**：`threads.sh` 读 docker daemon 的 NCPU+MemTotal 做二维分级（AI-009 §2.1），而 base.yml 只看 CPU。宿主 shell 被 cgroup 限 4c/8G 但 daemon 是 32c/123GiB 时，两条路径结论可能不同，文档却声称“分级表一致”，属误导。
- Docker `--memory` 不改写 `/proc/meminfo`（仍报宿主 123 GiB），因此只读 proc 会把 8 GB 容器误判为高配，必须读 cgroup v2/v1 限制。

## 2. 诊断依据

| 事实 | 来源 |
|---|---|
| `oe.utils.cpu_count()` 容器内可取到 32 | RV-020 §1.2 / ISS-037 |
| `/proc/meminfo MemTotal` 不随 `--memory` 变化 | 容器 cgroup 语义；AI-010 §2.1 |
| cgroup v2 `/sys/fs/cgroup/memory.max`、v1 `memory.limit_in_bytes` 反映容器内存上限 | cgroup 规范 |
| `threads.sh` 已按 CPU+内存二维分级，base.yml 未对齐 | AI-010 §1 复现（§1 只读 grep） |

## 3. 修复

新增两个 bitbake python 函数（CHG-022；放 `meta-yp-distro/classes/yp-concurrency.bbclass`，由 `kas/base.yml` 的 `INHERIT += "yp-concurrency"` 引入——bitbake ConfHandler 不接受 local.conf 多行 `def`，见 ISS-040）：

- `yp_mem_bytes(d)`：依次读 `/sys/fs/cgroup/memory.max`（v2）、`/sys/fs/cgroup/memory/memory.limit_in_bytes`（v1），值为 `max` 或 `>= 1<<60` 时回退 `/proc/meminfo MemTotal`。
- `yp_build_threads(d)`：CPU 用 `oe.utils.cpu_count()`（回退 `os.cpu_count()`，至少 1），内存用 `yp_mem_bytes(d)//GiB`，按二维分级：

| 级别 | 条件 | BB_NUMBER_THREADS | PARALLEL_MAKE |
|---|---|---|---|
| standard | cpus≥32 且 mem≥120GB | 32 | -j 16 |
| mid | cpus≥16 且 mem≥32GB | min(16,cpus) | -j max(1,threads//2) |
| small | cpus≥8 且 mem≥16GB | min(8,cpus) | -j max(1,threads//2) |
| legacy | 其他 | min(4,cpus) | -j max(1,threads//2) |

`PARALLEL_MAKE = "-j ${@max(1, int(d.getVar('BB_NUMBER_THREADS')) // 2)}"`，保证不出现 `-j 0`。

## 4. 修复前后矩阵

| 配置（cpu / mem） | 修复前 | 修复后 |
|---|---|---|
| 32 / 123 GB | 32 / -j16 | 32 / -j16（不变） |
| 4 / 8 GB | 4 / -j2 | 4 / -j2（不变，ISS-011 回退保留） |
| 16 / 16 GB | 16 / -j8（只看 CPU，内存不足仍高并） | 8 / -j4（small 降级） |
| 32 / 64 GB | 32 / -j16 | 16 / -j8（mid 降级） |
| 64 / 4 GB | 64 / -j32（必然 OOM） | 4 / -j2（legacy 兜底） |

分级逻辑纯 Python 复核 ALL_OK；容器 `bitbake-getvar` 实测见 RV-021 §2。

## 5. 影响面与取舍

- 标准机 32c/128G 结果不变（32/-j16）；仅中低配内存不足时自动降级，消除 OOM 风险。
- 不回退到 `os.environ.get`（ISS-037 已证 kas 隔离 env）；`YP_BUILD_THREADS` 不再是控制变量（ISS-039）。
- `threads.sh` 保留为 daemon 级诊断（输出 `SUGGEST_*`），分级表与 base.yml 语义一致，但明确标注非 bitbake 实际值。

## 6. 回滚

恢复纯 CPU 表达式会重现高 CPU 低内存 OOM 风险；不建议。如需回滚按 CHG-022 §回滚执行。
