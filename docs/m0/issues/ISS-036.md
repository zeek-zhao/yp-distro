## 1. 现象（只写观察到的事实）

- 观察到的输出／现象：
  - 执行 `--mode ghcr --manifest manifests/full-slices-manifest.json`，两片按 digest 拉取成功（part-00 `DIGEST_OK`、part-01 `DIGEST_OK`），但分片 01 校验失败：
    `ERROR: 分片 cache.slice.01 校验不符: bytes=2563463168/2563463168 sha256=fbe9e356...d54c/fbe9e356...d54`（字节数一致、sha256 表面一致却判不符）。
  - 经查 `manifests/full-slices-manifest.json` 中 slice 1 的 `sha256` 字段长度仅 **63 字符**，末尾缺 `c`；slice 0 字段为正确的 64 字符。
  - 从 GHCR 镜像（`sha256:899af6fa…`）实际提取 `cache.slice.01`：`sha256=fbe9e3567a87cc427a5e016b5e5b54c797ff8b2e4b4e6ebcbbe92bb47666d54c`（64 字符，`stat bytes=2563463168`）。manifest 字段是该真实值的 63 字符前缀（`real.startswith(field)=True`，缺 `c`）。
- 影响范围：`--mode ghcr` 全链路（fetch-cache.sh ghcr 段 + merge.sh 逐片 sha256 校验）永久失败；release 8 分片路径不受影响（另有 manifest）。
- 首次可见于：提交 `13ec6f5a`（该 truncated 值已进入历史）；因 `--mode ghcr` 从未真实端到端执行，缺陷一直潜伏。

## 2. 复现

```bash
python3 -c "import json;m=json.load(open('manifests/full-slices-manifest.json'));print(m['slices'][1]['sha256'],len(m['slices'][1]['sha256']))"
# fbe9e3567a87cc427a5e016b5e5b54c797ff8b2e4b4e6ebcbbe92bb47666d54 63
bash scripts/cache/fetch-cache.sh --mode ghcr --manifest manifests/full-slices-manifest.json \
  --dest-parent /tmp/e3 --work /tmp/e3-work     # 分片 01 sha256 校验不符 exit 1
```

- 期望结果：manifest 字段为 64 字符真实 sha256，ghcr 全链路 `SLICE_OK`/`MERGE_OK`/`SHA256_OK=a8870b50…`/`STRUCT_OK` 全过。
- 实际结果：分片 01 校验 exit 1，ghcr 链路中止。

## 3. 根因分析

- 直接原因：manifest slice 1 的 `sha256` 值在最初写入时被截断一位（末尾 `c` 丢失），成为无效哈希字段。
- 根本原因：`--mode ghcr` 全链路从未真实端到端执行（RV-014/015/016/017 均标 `UNVERIFIED`），该字段从未被真实分片 sha256 校验触发；静态检查只比对字段间一致性，未与真实资产比对。
- 排除过的假设及排除依据：
  - 排除“GHCR 分片损坏”：两片 `digest` 经 registry API 独立核验与 manifest 一致，实际提取的 `cache.slice.01` sha256 为合法 64 字符且与 `total_bytes`/`source_sha256` 体系自洽。
  - 排除“K-8 digest 拉取改坏”：第一片按 digest 拉取并 `DIGEST_OK`、分片校验通过；失败发生在第二片的 sha256 字段比对，与拉取方式无关。

## 4. 修复

- 修复方案（CHG-020）：将 `manifests/full-slices-manifest.json` 中 slice 1 的 `sha256` 字段由 63 字符截断值补全为真实 64 字符值 `fbe9e3567a87cc427a5e016b5e5b54c797ff8b2e4b4e6ebcbbe92bb47666d54c`。这是**笔误修复**（补足被截字符使其与真实资产一致），不是篡改校验值：`bytes`、`digest`、`total_bytes`、`source_sha256`、`total_slices` 均不变。
- 同时 CHG-020 记录 K-8 的 `fetch-cache.sh` 改造（check_target 前置、按 digest 拉取、RepoDigests 校验、DIGEST_FALLBACK 回退）。

## 5. 关闭证据（Verifying → Closed）

- 修复后重跑 `--mode ghcr` 全链路：待 RV-018 E3 记录（预计 `DIGEST_OK`/`SLICE_OK`/`MERGE_OK`/`SHA256_OK=a8870b50…`/`STRUCT_OK` 全过）。
- 关闭条件：ghcr 全链路真实通过，且 manifest 的 `bytes`/`digest`/`total_bytes`/`source_sha256` 与修复前逐字节一致（仅 sha256 字段补 `c`）。
