# 记录与文档管理规范（对齐 ISO，非认证声明）

> **性质说明**：本文件规定的是**可审计的记录结构**，按 ISO 9001:2015 的文件化信息要求、ISO/IEC/IEEE 12207 的生命周期过程划分、ISO 10007 的配置管理思路组织；本工程未申请任何 ISO 认证，文中不出现「已认证」「符合某条款」的结论性表述。

## 1. 为什么要有这一层

嵌入式发行版的问题不是「写不出代码」，而是半年后没人能回答：这个阈值为什么是 8 GB、那次构建为什么失败、谁批准放宽了检查、这条需求最终落到哪个提交。ISO 那套要求的实质就是**让每个结论都能追到证据、每个变更都能追到批准**。这里只取这一层，不做形式主义文档。

## 2. 文档分类与编号

| 类别 | 前缀 | 用途 | 存放 |
|---|---|---|---|
| 计划 | `YP-M0-PLAN-` | 阶段计划、进度、出口判据 | `docs/m0/` |
| 设计 | `YP-M0-DES-` | 每个 Step 的目的、接口、失败模式、验收命令 | `docs/m0/design/` |
| 决策 | `YP-M0-ADR-` | 一次性技术取舍（含被否方案与理由） | `docs/m0/adr/` |
| 评审 | `YP-M0-RV-` | 设计评审与代码评审记录 | `docs/m0/reviews/` |
| 问题 | `YP-M0-ISS-` | 过程问题与解决过程 | `docs/m0/issues/` |
| 变更 | `YP-M0-CHG-` | 阈值、契约、接口的变更 | `docs/m0/changes/` |
| 验收 | `YP-M0-REC-` | 阶段验收与证据 | `docs/m0/acceptance.md` |

编号三位递增，不复用、不回收。删除某文档时状态改 `Obsolete` 并保留文件，不做物理删除。

## 3. 文档头（每份文档必须带）

```text
| 文档编号 | 版本 | 状态 | 责任人 | 生效日期 | 关联 |
```

状态取值：`Draft` → `In Review` → `Approved` → `Obsolete`。进入 `Approved` 必须有对应 `RV-` 评审记录；`Obsolete` 必须写明被哪份文档取代。

每份文档尾部必须有**变更记录表**（版本 / 日期 / 变更 / 作者），只追加，不改写历史行。

## 4. 可追溯链（需求 → 证据）

M0 的追溯链固定为五段，缺一段即视为记录不完整：

```text
PRD 需求编号（B-01…）
  → 设计文档（YP-M0-DES-0NN 标注覆盖的需求编号）
  → 实现提交（提交信息 Refs: YP-M0-DES-0NN）
  → 验证证据（命令、日志、报告路径）
  → 验收条目（YP-M0-REC-001 判据表行）
```

`docs/m0/traceability.md` 维护这张矩阵；每次新增设计或提交后同步更新，评审中不一致直接打回。

## 5. 问题与解决过程的记录方法

**触发**：任何非预期现象——构建失败、脚本报错、镜像拉取失败、权限异常、耗时异常、结果与文档不符。

**流程**（先记录后修复，不允许修完再补）：

```text
New → Analyzed → Fixing → Verifying → Closed
                    ↘ Duplicate / Won't Fix（须写明理由与批准人）
```

**记录要求**：

- 现象只写观察到的事实，不写猜测
- 必须能复现：给出镜像 tag、提交号、层清单、完整命令
- 根因与措施分开写；临时措施与永久措施分开写；只做临时措施的，必须留后续项
- 关闭前必须有验证证据（命令输出摘要或日志路径），禁止「看起来好了」
- 每条问题结束回答一句：**下次如何避免**，可复用经验汇总到 `docs/m0/lessons.md`

**修复提交**：`fix(m0): <动作>` + `Refs: YP-M0-ISS-0NN`；未带引用的修复视为记录断裂。

## 6. 变更控制

以下变更必须先开 `CHG-` 单并获批，再动代码：

| 变更对象 | 例子 |
|---|---|
| 阈值与配额 | 切片上限、缓存保留周期 |
| 对外契约 | 变量名、目录布局、镜像标签规则 |
| 门禁规则 | 新增/放宽 CI 检查 |
| 依赖基线 | 上游层 tag、kas 版本、基础镜像 |

变更单必须写：变更内容、原因、影响面、回滚方式、验证方式、批准人。

## 7. 记录保存与完整性

- 全部记录随代码入库，靠 Git 历史保证不可抵赖；不使用外部系统作为唯一副本
- 二进制证据（日志、报告）不入库，入库的是路径 + 摘要 + 关键片段，原文存放位置在记录中写明
- 密钥、token、内网地址一律不入库；发现泄漏按信息安全事件处理，记录 `ISS-` 单但不写明文

## 8. 评审怎么做（不做形式评审）

评审记录 `RV-` 只回答四问：设计是否覆盖需求、失败模式是否列全、验收命令是否可执行、回滚是否可行。四问缺一即 `In Review` 不通过，不允许「整体感觉可以」通过。
