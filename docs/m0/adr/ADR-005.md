|---|---|
| 文档编号 | YP-M0-ADR-005 |

## 编号说明

`m0-resume-prompt.md` §9.1 要求新建 `ADR-004.md` 裁决分片发布契约，但 `ADR-004` 已在 Stage B 用于「kas 目录结构与分层策略」（状态 Approved，已随提交 `5e0xxxx` 发布）。覆盖历史决策会破坏追溯链，故本决策顺延为 **ADR-005**，并在 DES-008 与 plan.md 记录该编号调整。决策内容即为 §9.1 要求的二选一裁决。

## 背景

S6 已产出 `pack.sh` / `split.sh` / `merge.sh`，能把 `cache.tar` 切成 ≤`SLICE_MAX_BYTES` 的分片并做完整性校验。但这些分片尚未接入 S7 发布链路（RV-010 F-07），判据 7 因此悬空。分片以何种形态发布到 GHCR 属于**契约变更**，须先裁决。

## 决策

采用 **方案 1：每片一个独立镜像 tag**，不采用方案 2（OCI artifact）。

| 项 | 约定 |
|---|---|
| 分片 tag | `yp-cache:wrynose-m0-part-00`、`-part-01`…（两位序号，从 00 递增） |
| 清单 | `manifest.json` 随分片一并发布，作为 GHCR release 附件 |
| 分片内容 | 每片作为单个文件 COPY 进最小 alpine 镜像（`/work/slices/cache.slice.NN`），可供匿名 `docker pull` |
| 下载侧 | 逐片 `docker pull` → `docker create` + `docker cp` 取出 → `merge.sh` → 源 sha256 比对 |
| 清单字段 | 在 DES-006 原有字段上新增 `source_sha256`（源 tar 的 sha256），供 merge 后比对 |

## 理由

1. **与验收口径一致**：`m0-resume-prompt.md` §9.3 给出的拉取命令是 `docker pull ...-part-00`，方案 1 直接匹配，不需改写验收命令。
2. **复用已验证能力**：B-08 已证实 GHCR 镜像 tag 可被匿名拉取（公共仓库 + Actions `GITHUB_TOKEN` 发布）。分片沿用镜像 tag 可复用同一套登录/发布/拉取路径，无需引入 oras CLI 与新权限模型。
3. **下载侧简单可靠**：`docker cp` 取文件是标准操作；方案 2 需要下载侧也安装 oras，违反「只装 Docker 的机器即可构建」的 M0 目标。

## 被否方案

**方案 2（OCI artifact / `oras push`）**：虽原生支持任意 blob 与单一引用，但要求发布与下载两端都安装 oras CLI，增加 M0 的运行时依赖；且分片是二进制切片而非容器 rootfs，用 OCI artifact 的收益（单一引用）不足以抵消工具链成本。留待后续里程碑若引入通用 artifact 分发再评估。

## 后果

- 分片数随缓存体积增长，tag 数线性增加；`manifest.json` 的 `total_slices` 决定拉取循环次数。
- 每个分片镜像含一层 alpine 基线开销（约 3 MB），相对单片 ≤8 GB 的载荷可忽略。
- workflow 需新增 `publish-cache-slices` job，串联 `pack → gen-meta → split → 上传各片 + manifest → 记录 digest`。
- 空壳 `yp-cache:wrynose-m0` 镜像的结论必须降级为「基线布局已验证，真实载荷待 S5 产物」（F-02），不得称「预热缓存完成」。
- 受 L-01 遗留约束（孤立分支 workflow 不可 dispatch），本次仅完成接线与本地脚本链路验收；workflow 端到端触发标 `UNVERIFIED` 并说明原因，不伪造通过。
